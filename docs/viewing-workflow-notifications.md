# Durable bell notifications and rollout review (Phase 9)

## Four separate concepts

Current deployment/schema decisions are in [rollout finalization](viewing-workflow-rollout.md).

Messages/chat retain their existing dedicated unread/read state and icon. The bell is a durable record of selected user-facing events. Attention is derived exclusively from unresolved actions. Verlauf remains the complete authorized application history, including technical activity that does not belong in the bell. Reading a notification changes none of the other three concepts.

## Persistent model and event policy

`notifications` stores a UUID, recipient/side, application/listing identifiers, immutable source activity ID, allowlisted activity type, optional workflow/proposal/appointment IDs, section, occurrence/creation time, nullable `readAt`, and `expiresAt`. It stores no names, titles, notes, proposal messages, rejection explanations, dates copied from appointment DTOs, profile/document information or UI URLs. The HTTP DTO adds a structured `OPEN_HISTORY` target containing the source `activityId`; the frontend fetches current authorized history/capabilities before presenting actions. Legacy proposed ledger IDs are not invented as confirmed appointment targets.

The source activity and notification share the domain transaction. Bulk history receives explicit stable IDs before insertion so notifications reference the actual immutable rows. A unique `(source_activity_id, recipient_id)` prevents duplicate inbox items; replay never resets read state or retention. Composite foreign keys enforce the activity/application and application/listing scope. Notification failure rolls back domain state, history, receipts and outbox together. Socket delivery has no influence on whether a notification exists. No historical activity is backfilled into the inbox, and no legacy appointment/deadline is fabricated.

| Creates a bell item                                                             | Recipient policy                                                                    |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Viewing invitation, applicant alternative, provider replacement/counterproposal | Other authorized side                                                               |
| Proposal acceptance or standalone rejection                                     | Other authorized side                                                               |
| Applicant withdraws a pending alternative                                       | Provider                                                                            |
| Applicant cancellation or provider cancellation/flow close                      | Other authorized side                                                               |
| Completed viewing, attributed absence/no-show, outcome correction               | Applicant; provider already performed the action                                    |
| Applicant STILL_INTERESTED                                                      | Provider                                                                            |
| Provider CONTINUE_CONSIDERING                                                   | Applicant; already shared by existing HTTP/history policy                           |
| Application rejected, restored, withdrawn, accepted for rental, promoted ACTIVE | Authorized side(s), excluding the actor; SYSTEM can notify both visible sides       |
| Proposal expiry                                                                 | Both currently authorized sides                                                     |
| 48h unanswered interest timeout                                                 | Real SYSTEM `APPLICATION_REJECTED` notification, not an extra technical expiry item |
| Listing archived/unpublished while a proposal/appointment is closed             | Applicant; only when the closure actually references a commitment                   |

**Explicitly excluded:** chat/messages/read receipts/reply settings; document/profile activity; initial application submission; provider UNDECIDED; generic technical workflow closures without a user-facing listing commitment; reconciliation and ordering bookkeeping; the extra RESCHEDULED history row accompanying acceptance; the decline half of an atomic counterproposal; the technical interest-declined row accompanying withdrawal; the technical interest-expired row accompanying SYSTEM rejection; INTERNAL activity; own-action receipts. DO_NOT_CONTINUE uses its real application rejection item. These history entries remain in Verlauf. A private internal `counterproposal` metadata flag suppresses the duplicate decline; it is omitted from public activity and socket payloads.

No-show notifications are historical attendance events, not global reputation or a new penalty. A later correction creates a correction notification and retains the prior event; clients must fetch current outcome history rather than treat an old bell item as the current truth. Never render NO_SHOW as applicant absence without checking that outcome's attribution. No personal/provider cancellation explanation or absence attribution is copied into the bell payload. Repeated CONTINUE_CONSIDERING commands for the same appointment do not create another bell item while its existing notification is retained; each command still remains in history.

## Current authorization

An inbox necessarily stores its recipient at event creation; a personal read state cannot be reconstructed from delivery-time routing alone. Creation checks role, active user status, activity audience and current application/provider visibility, excluding the acting side. Read/list/count operations independently recheck current identity, recipient role/status, application ownership and the existing provider visibility policy. WAITING is always hidden from providers; never-active hidden terminal applications also stay hidden. Terminal applications that remain visible under existing history rules keep their notification history.

Hidden rows contribute neither content nor count and cannot be marked read. Mark-all likewise leaves them untouched. If visibility returns, an unread item can reappear with the same identity and read state. Restore to WAITING notifies the applicant without revealing that applicant to the provider. Removed listing ownership immediately prevents old inbox access; historical personal inboxes are not reassigned to a new owner. Suspended/deleted/changed-role recipients cannot access mismatched inbox entries. As with existing HTTP reads, authorization is evaluated against a database snapshot; future ownership-transfer features still need former-owner cache invalidation described in Phase 7.

## HTTP contract

All routes use the existing authenticated session guard and main application's CSRF/validation configuration:

- `GET /api/v1/me/notifications?limit=25`: bounded limit 1–100; returns schemaVersion 1, `asOf`, `items`, authorized `unreadCount`, `nextRevalidateAt` and `nextCursor`.
- Optional `category=APPLICATION|VIEWING|DOCUMENTS` filters items before pagination. Invalid categories return 400. Keep that filter when following `nextCursor`. `unreadCount` remains the global currently authorized bell count, and `nextRevalidateAt` remains its earliest visible expiry, independent of this filter.
- Every item adds derived `category` to existing `id`, raw `type`, schemaVersion, `occurredAt`, `createdAt`, nullable `readAt`, `expiresAt` and structured `target`. Category comes from the activity type; no category column or new notification-producing rule is added. DOCUMENTS is supported for filtering but currently returns no items because document notifications remain deferred.
- Group by `target.applicationId` / `target.listingId`. Open the exact authorized history entry using `target.activityId`, section and optional workflow/proposal/appointment IDs. Retain `OPEN_HISTORY`; fetch current attention/capabilities separately. There is no duplicated `actionable` flag or presentation text. Notification means something happened; attention means something still requires action.
- Pagination uses both `beforeCreatedAt` and `beforeId`, ordered by `(createdAt DESC, id DESC)`; ties are deterministic and no other user's cursor grants access.
- `GET /api/v1/me/notifications/unread-count`: returns `asOf`, authorized `unreadCount` and `nextRevalidateAt`. This count is exclusively for the bell.
- `POST /api/v1/me/notifications/:notificationId/read`: idempotently sets the first read time; foreign/hidden/missing items return the same 404.
- `POST /api/v1/me/notifications/read-all`, body `{ "throughCreatedAt": "<asOf from inbox>" }`: marks currently visible unread rows created through that snapshot. Newer and hidden items stay unread; future snapshots are rejected. Returns `markedCount`.

Each item contains `id`, `type`, schemaVersion 1, `occurredAt`, `createdAt`, `readAt`, `expiresAt`, and target `{ applicationId, listingId, workflowId, proposalId, appointmentId, activityId, section, action: OPEN_HISTORY }`. Optional identifiers are null when unavailable. Targets identify history, never grant permission or promise that the old action is still possible. Notification read writes do not advance workflow revision, resolve attention, mark messages read or affect consideration priority.

## Realtime and retention

Creation shares existing transactional `application.viewing.changed` / `application.lifecycle.changed` hints, including the redacted provider listing hint when application access is removed. Consumers must also refetch the bell on those hints; do not derive counts from socket events. Offline notifications remain in PostgreSQL and are fetched at next login/reconnect/focus.

Read-state changes write a transactional **user-scoped** `notifications.changed` outbox event. The scope constraint requires user ID, null application ID and null conversation ID. Wire shape is `{ eventId, type: notifications.changed, schemaVersion: 1, occurredAt, userId, payload: {} }`; no item ID, count, state or application identity is broadcast. Existing authenticated transport/session checks deliver it only to all eligible tabs of that current active user, with a final user-status/role check. Existing conversation/application payloads stay unchanged. Duplicate/out-of-order hints only trigger HTTP refetch. No new socket system, client domain events or replay is introduced.

Retention is **90 days from database creation** (`createdAt + interval '90 days'`, exposed as exact `expiresAt`; production database sessions must use UTC to avoid daylight-saving shifts) for read and unread items alike. Resolution or terminal lifecycle does not delete/mark them read. Expired items disappear immediately from reads/count; `nextRevalidateAt` is the earliest visible expiry for client refresh. A local poller deletes at most 500 expired rows every minute outside tests, based on the database clock. Cleanup can lag without exposing expired content. Source activity/history is never removed by inbox cleanup. Actual user/application/activity deletion cascades its notification rows. Failed cleanup logs `NOTIFICATION_RETENTION_FAILED` and retries the next minute. No dismissal/unread-again endpoint is introduced in this minimal foundation.

## Phases 1–9 rollout and compatibility review

1. Back up and review the migration ledger on the target database. Deploy all approved additive migrations in order; never reset or silently reconcile a divergent deployed ledger. This phase adds an empty notification table, scoped foreign keys/indexes and user-scoped outbox support. Existing history/outcome IDs and queued conversation/application events remain unchanged.
2. Pause old outbox dispatchers and avoid mixed-version mutation traffic during this deployment. Apply migrations **before** starting the updated producer/consumer/API. The composite activity index builds transactionally and can block writes on a large history table; use a cutover window and rehearse production-volume timing. Old parsers cannot handle `notifications.changed`, and old non-null application outbox contracts cannot represent it. Domain writes after activation must run through the updated activity writer; running old producers alongside it would leave notification gaps. No retrospective notification replay/backfill is promised.
3. Start one updated API instance and verify HTTP session/CSRF behavior, notification reads, viewing commands, expiry and dispatcher health. `REALTIME_ENABLED=true` plus `OUTBOX_DISPATCH_ENABLED=true` are required for connected delivery; offline inbox persistence works with dispatch disabled. `VIEWING_EXPIRY_ENABLED` defaults true outside tests (30s, batch 50). Retention starts outside tests automatically. Monitor notification failures as domain-write failures, expiry lag, outbox backlog and retention errors.
4. LEGACY remains a live compatibility path; imported projections are not authoritative until explicit safe reconciliation. Old commands are blocked for CURRENT workflows. Reconcile under existing listing/application locks, preserve IDs and close historical commitments on termination/restore. Do not bulk-switch modes, revive old appointments or retire legacy routes while legacy clients/data still depend on them. This phase adds no global enable/disable feature flag for the new command endpoints.
5. Backend notification durability is implemented; **frontend rollout still requires** wiring the bell APIs, auth-safe history/deep links, app/listing/user invalidation handlers, expiry revalidation and reconnect/focus refetch. Socket state remains advisory. This task does not implement or deploy frontend UI, retire live legacy clients or enable traffic.
6. API replica #2 still requires shared cross-instance fanout integrated with local authorized socket delivery/session revocation. Database outbox claims and sticky sessions alone are insufficient; adding an adapter without changing local socket enumeration is insufficient. No Redis is added in this phase.
7. Roll back application code conservatively while retaining additive schema/data. Do not restore `application_id NOT NULL` while user-scoped events exist, drop notifications, discard undispatched rows or convert CURRENT data back to legacy. Keep a compatible consumer; disable dispatch and viewing/lifecycle mutation traffic if the rolled-back code cannot honor the current contract. Disabling expiry during a rollback delays durable transitions, but deadline-derived HTTP capabilities still need a compatible reader/command layer. Existing committed history/read states must survive rollback.

Schema/migration was applied only to the dedicated E2E database during implementation. All 43 migrations were also rehearsed successfully in a newly created isolated schema in that database; only the temporary schema was removed afterward, without resetting existing E2E tables. Deployment and production migration are operator actions, not performed by this task. Production-volume sizing and a rehearsal on a production-equivalent copy remain deployment checks.

Phase D aligns Prisma metadata with the existing migration SQL for the earlier timestamp, FK action, UUID-default and index-name differences. All 43 migrations replay successfully with an empty representable diff; no data conversion or migration was introduced. See [canonical schema and rollout](viewing-workflow-rollout.md) for custom invariants, deployment configuration and manual rollback assumptions. Production ledger verification remains a deployment check.

## Deferred reminders and remaining product edges

No reminders are implemented: confirmed appointment reminders (likely 24h/2h before) and a provider decision reminder after applicant interest are explicit follow-ups. Reminder creation will need exact appointment/revision/deadline identity and deduplication, cancellation on replacement/closure, timezone handling and a policy for short-notice appointments. They must not reuse bell unread count as attention.

Repeated independent schedule changes are separate real events and can still produce several unread items; there is no lossy collapse of historical notifications. Any future grouping must preserve stable source/read identities. Explicit CONTINUE_CONSIDERING is already shared by current HTTP/history; changing it to private provider triage requires changing all those contracts together, not merely suppressing the bell. Email/push and global applicant reputation remain outside this foundation.
