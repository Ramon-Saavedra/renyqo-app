# Viewing lifecycle integration (Phase 4)

> This page records its implementation phase. Phases 1–9 are complete; see [current rollout and schema](viewing-workflow-rollout.md) for deployment status and follow-ups.

Phase 4 integrates the new workflow with existing domain transitions. No Phase 5 priority changes, realtime/outbox, expiry worker or durable notification delivery are included.

## Integration and transactions

`ViewingLifecycleService`, provided/exported below orchestration by ApplicationsModule, joins the caller-owned Serializable transaction. Application withdrawal and provider rejection reuse the existing Phase 1 helpers. Eligibility revalidation, selected rental acceptance, every application on a rented listing, listing archive and moving a listing to DRAFT now close viewing commitments in the same transaction as their real lifecycle changes. Provider rejection retains real `NOT_SELECTED`, listing events, curation rate limit, admission cooldown and waiting promotion. Applicant withdrawal retains existing capacity/promotion behavior. Archive/DRAFT close viewing commitments without inventing application rejection reasons or changing the listing's existing application status semantics. PAUSED remains part of the active process; pause/resume preserves appointments.

Listing status commits now use Serializable transactions and the same listing lock as viewing commands/rental selection, retaining their optimistic source-status check. Bulk closure visits application IDs in stable order. Closure locks listing → application → workflow; no service starts a nested transaction. Profile update now locks all relevant ACTIVE/WAITING listings in sorted order before writing its profile, correcting the existing profile-before-listing inversion against admission/promotion/revalidation. Serializable retries cover applications admitted while that snapshot was being read.

CURRENT closure resolves pending offers as CLOSED, cancels future commitments with attributed `APPLICATION_ENDED`, closes outstanding interest requests, clears pointers and increments revision. Activities and all domain effects roll back together on any failure. Already terminal proposals, appointments, outcomes, responses and activities remain immutable. `VIEWING_WORKFLOW_CLOSED` records the actual new lifecycle closure, actor, reason, affected targets and revision; it is distinct from rejecting an offer, ordinary calendar cancellation, application rejection and applicant withdrawal.

Started appointments are not fabricated cancellations or no-shows. The additive `OUTCOME_PENDING` ledger status retains acceptance/schedule/history while removing the calendar commitment pointer, so attendance can be resolved later. It requires a real accepted timestamp; CURRENT consistency checks allow it. Normal applicant cancellation remains strictly before start. Two additive migrations introduce enum values/activity types and update the consistency function; there is no historical closure/deadline backfill.

## Restore and legacy

Restore keeps the existing eligibility, latest-attempt, cooldown, capacity and WAITING privacy rules. It increments the workflow revision, resets persisted provider non-selection to UNDECIDED, and leaves old commitments closed. ACTIVE restoration needs a fresh provider invitation. WAITING remains hidden from the provider, including the workflow endpoint. Previously unread messages and stored applicant reply settings are preserved; effective permissions/unread relevance are recomputed from application/listing state.

LEGACY closure operates on the actual ledger, never snapshot pointers. It refreshes existing imported proposal resolutions from the guarded canonical source, retains mode LEGACY and records only the actual present closure. It invents no historical proposals/deadlines or actors. Restore repairs any still-live pre-integration legacy commitment before restoring eligibility. Explicit reconciliation remains required to use current commands. Authorized reconciliation can also run on a terminal application for attendance/history; it closes any pre-integration outstanding commitments at the actual reconciliation time before returning CURRENT. It cannot revive them. Each actual lifecycle transition increments an existing workflow revision, even if its calendar flow was already closed. Existing lifecycle command guards prevent duplicate terminal effects; restore also changes revision to invalidate stale intents.

## Decisions and minimal command additions

These POST routes share the existing `/api/v1/{side}/applications/:applicationId/viewing-workflow` base and require exact appointment ID, UUID `requestKey`, integer `expectedWorkflowRevision`, durable retry semantics and structured state conflicts:

The command GET snapshot now also exposes `postViewing` with the latest completed appointment ID, persisted interest state/deadline, provider consideration and response blocker. It does not replace the later comprehensive attention/capability projection.

| Side      | Route                                        | Input beyond command identity                                                                          |
| --------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Provider  | `/appointments/:appointmentId/outcome`       | `outcome: COMPLETED or NO_SHOW`, `absenceSide` required only for NO_SHOW; optional `correctionReason`  |
| Applicant | `/appointments/:appointmentId/interest`      | `interest: STILL_INTERESTED or NOT_INTERESTED`; NOT_INTERESTED requires JSON `confirmWithdrawal: true` |
| Provider  | `/appointments/:appointmentId/consideration` | `consideration: CONTINUE_CONSIDERING, UNDECIDED or DO_NOT_CONTINUE`                                    |

The outcome command is the minimum prerequisite for meaningful current post-viewing decisions: it records completion, opens the real deadline and retires the calendar pointer. Attendance requires appointment end. Original outcome plus at most one opposite-outcome correction remain append-only; correction retains the existing 24-hour limit and is forbidden after an interest response or a newer accepted round. No-show attribution is structured; ACTIVE order is unchanged until Phase 5. Recording a detached older attendance outcome cannot clear newer pointers or open an obsolete interest deadline. Recording an outcome after lifecycle termination never reactivates the application or requests interest.

Completion in an active process opens interest for 48 elapsed hours from recorded completion. A newer completion closes earlier pending interest deadlines. Interest/consideration target the latest completed viewing, allowing its outstanding response while another future appointment exists. Applicant disinterest creates the response and calls real withdrawal in the same transaction, closing any future commitments and applying promotion. Provider DO_NOT_CONTINUE persists consideration with the real NOT_SELECTED rejection in one workflow revision; rejection failure rolls back the decision. Continue/undecided do not reject the application. Responses and decisions remain in history after closure/restore. Existing legacy interest endpoint additionally accepts `confirmWithdrawal: true`; disinterest without confirmation is rejected, and confirmed disinterest now uses the same real withdrawal. Legacy unanswered interest gains no invented deadline at cutover.

## Worker-ready timeout transition

`ApplicationLifecycleService.expireViewingInterestWithinTransaction(tx, applicationId, appointmentId, expectedWorkflowRevision, now)` is an internal caller-owned transaction operation, not a user endpoint or scheduled worker. It returns false for stale revision/target, a nonpending response, an unexpired deadline or inactive application/listing. At the exact deadline it marks interest EXPIRED, records SYSTEM history, rejects with `POST_VIEWING_RESPONSE_EXPIRED`, closes other commitments and applies capacity/promotion atomically. Retry cannot duplicate effects. The terminal status is REJECTED, not voluntary WITHDRAWN or provider NOT_SELECTED. This reason creates no provider cooldown; existing legitimate provider cooldown history is not erased. Existing provider restore remains restricted to NOT_SELECTED; eligible fresh reapplication after system timeout is allowed. The Phase 8 worker now discovers due requests and rechecks their current revision under locks.

## Cross-domain state and remaining phases

No conversation messages/read markers or stored reply preferences are deleted/toggled on rejection/restore. Existing process policy makes terminal application/listing state read-only, removes actionable unread relevance/attention, and recomputes cards/workspaces through the existing read-model chain. Tests verify unread relevance returns after restore while the viewing stays closed. Phase 7 lifecycle invalidation now refreshes these dependent surfaces together. Current negotiated viewing/interest attention projection is still the approved read-model phase; this phase does not redesign it.

Phases 5–9 now implement ACTIVE no-show ordering, attention/deep links, realtime/outbox, expiry and durable notifications. Production activation still requires the deployment configuration and frontend wiring described in the rollout reference. Additional product cases to decide: account suspension/deletion or administrative listing removal, whether successful rental ends the applicant's applications to other listings, and operational reminders/escalation for attendance awaiting an outcome after termination. No such cross-listing or account policy is inferred here.

Tests cover each terminal trigger, restore ACTIVE/WAITING, real decision exits/promotion, boundary deadlines, outcome correction, LEGACY closure/cutover, unread/reply preservation, rollback, and lifecycle races against acceptance/replacement/cancellation/rejection/withdrawal/rental selection. A calendar action and subsequent terminal lifecycle action may both succeed in serial order; no contradictory commitment survives. Competing terminal lifecycle decisions permit only one winner.

## Pre-PR Phase A: correctness cleanup

Provider close now rejects an empty calendar flow with structured `409 VIEWING_STATE_CHANGED` / `NO_OPEN_VIEWING`, matching the read capability. It writes no revision, history or outbox event on rejection.

Lifecycle termination closes unanswered imported `LEGACY_UNANSWERED` decisions as well as normal `PENDING` interest. Unrequested decision metadata is also closed at a real lifecycle boundary, so resolving/correcting old attendance after restore cannot create a new response window. Restore and a fresh invitation cycle repair unanswered decision metadata left by pre-fix closed workflows; no historical deadlines are invented. A newer outcome supersedes earlier unanswered legacy interest. Recording attendance for an old `OUTCOME_PENDING` visit remains possible, but cannot reopen interest in that ended process.

A fully historical closed workflow is not closed again: its closure date/reason, revision, ledger, outcomes, activities and viewing outbox stay unchanged. A calendar-only `PROVIDER_CLOSED` flow can still carry a legitimate earlier completed-viewing decision, as already approved. A later application/listing termination closes that decision and advances revision without overwriting the calendar closure date/reason or manufacturing another closure activity. Old LEGACY snapshots with genuinely live ledger commitments can still be cleaned up while preserving any existing closure date/reason.

Restore cleanup keeps PROVIDER as its real executor. Its `VIEWING_WORKFLOW_CLOSED` activity carries allowlisted `viewingLifecycleContext: RESTORE_CLEANUP`; it does not create an `APPLICATION_REJECTED` activity. The accompanying real restore records the application transition. Existing private reason filtering and notification rules are unchanged.

Phase B aligns the expiry selection/helper gates for legitimate interest behind calendar-only `PROVIDER_CLOSED`, with 48-hour SYSTEM rejection, capacity/promotion and historical-closure regression coverage. See [expiry processing](viewing-workflow-expiry.md) for fair sweeps and retry behavior.
